# 배송 알림 (Wi-Fi 서명 기반)

문앞 Wi-Fi 서명을 회원별로 저장해 두고, 배송 중 같은 문앞에 일정 시간 머무르면
배송 완료 문자를 발송하는 안드로이드 앱.

좌표를 추정하는 실내 측위(fingerprinting)가 아니라 **재식별(re-identification)** 방식이다.
"여기가 지난번 그 집 문앞이 맞나"만 답하면 되므로 사전 격자 서베이가 필요 없고,
첫 방문이 곧 학습이 된다.

## 구성

| 경로 | 역할 |
|---|---|
| `model/Member.kt` | 회원 + AP 서명 데이터 모델 |
| `data/MemberStore.kt` | JSON 파일 저장소, 서명 EMA 갱신, 운영 파라미터 |
| `wifi/WifiScanner.kt` | 스캔 래퍼(스로틀링 대응), 서명 누적기 |
| `wifi/SignatureMatcher.kt` | 매칭 점수 계산, 체류 판정 |
| `service/DetectionService.kt` | 운영 모드 포그라운드 서비스 |
| `sms/SmsSender.kt` | 문자 발송 + 확인 모드 리시버 |
| `ui/` | 회원 목록, 수집, 서명 확인, 라이브 매칭, 정답 기록, 튜닝 |
| `wifi/ParamTuner.kt` | 정답 라벨 기반 파라미터 재탐색 |
| `wifi/ApIndex.kt` | AP 희소성(IDF) 지수 |
| `wifi/PressureTracker.kt` | 기압계 기반 층 구분 |
| `wifi/RouteScope.kt` | 배송 순서로 후보 좁히기 |
| `data/ZoneStore.kt` | 사무실 구역 + 배송 완료 처리 단일 창구 |
| `nfc/NfcHelper.kt` | 태그 읽기 + Wi-Fi 교차 검증 |
| `sms/MessageComposer.kt` | 문구 작성 + 광고 규제 강제 |
| `telemetry/` | 오프라인 큐 + 배치 업로드 |
| `server/` | BigQuery 스키마 + 수집 엔드포인트 |

## 빌드 — 폰에 설치하기

### 방법 A. GitHub Actions (Android Studio 없이)

리포에 올리고 Actions 탭 > Build APK > Run workflow.
끝나면 Artifacts에서 `app-debug-apk`를 받아 폰에 설치한다.
설정 > 보안 > 출처를 알 수 없는 앱 설치 허용이 필요하다.

리포 Settings > Secrets에 세 개를 넣어두면 빌드 시 주입된다.
안 넣어도 빌드는 되고, 텔레메트리만 로컬 큐에 쌓인다.

| Secret | 용도 |
|---|---|
| `INGEST_ENDPOINT` | 수집 엔드포인트 URL |
| `INGEST_API_KEY` | 엔드포인트 인증 키 |
| `BSSID_SALT` | BSSID 해시 솔트 (임의 난수) |

### 방법 B. Android Studio

열고 Run. `compileSdk 35` / `minSdk 26`.
텔레메트리를 붙이려면 `~/.gradle/gradle.properties`에:

```
ingestEndpoint=https://...
ingestApiKey=...
bssidSalt=...
```

솔트와 키는 절대 리포에 커밋하지 말 것.

Play 스토어 배포용이 아니다. `SEND_SMS` 권한을 쓰는 앱은 스토어 등록 제한이 크므로
APK 직접 설치 또는 MDM 배포를 전제로 한다.

## 필수 단말 설정

**개발자 옵션 > 네트워킹 > Wi-Fi 스캔 제한 → 끄기**

안드로이드 9 이상은 포그라운드 앱 기준 2분에 4회로 스캔을 제한한다.
제한에 걸려도 예외가 아니라 직전 결과가 그대로 반환되기 때문에,
이걸 끄지 않으면 수집은 한없이 느려지고 체류 감지는 30초 해상도로 떨어진다.
MDM으로 일괄 적용해야 실사용 가능하다.

백그라운드 앱은 전체 합산 30분에 1회다. 그래서 이 앱은 반드시 포그라운드 서비스로 돈다.
상단 상주 알림은 없앨 수 없고, 없애서도 안 된다 — 근무 중 위치가 수집되고 있다는 사실이
당사자에게 보여야 한다.

## 사용 흐름

1. 회원 추가 (이름 / 번호 / 동·호수)
2. 해당 집 문앞에서 회원 탭 → 신호 수집 → 12라운드 (약 40초)
3. 운영 모드 켜기 → 배송 중 자동 탐지
4. 조건 충족 시 알림 → 탭하면 발송 (확인 모드) 또는 즉시 발송 (자동 모드)

## 확인 화면 두 가지

### 서명 확인 (회원 탭 > 서명 확인)

저장된 서명을 실시간 스캔과 나란히 놓고 보여준다.

```
 AP                 저장  현재       Δ  빈도
 KT_GiGA_2G        -48.3   -51   Δ -2.7 100%
 SK_WiFiGIGA1F     -61.0   -59   Δ +2.0  92%
·iptime_A          -78.5    --   미관측  40%
```

`Δ`가 크게 벌어진 AP가 오탐의 원인이다. 특정 AP만 계속 어긋나면
그 공유기가 교체됐거나 위치가 바뀐 것이므로 재수집 대상이다.
`·` 표시는 빈도 50% 미만이라 매칭에서 제외되는 AP다.

### 라이브 매칭 (메인 > 라이브 매칭 확인)

전체 회원 서명에 대해 지금 점수가 몇 점씩 나오는지 순위로 보여준다.

```
✔ 확정  —  일치 0.78
마진 0.221 (기준 0.10) · 관측 AP 23개 · 14회 스캔

회원          점수   커버  RSSI 앵커
▶김OO        0.781  0.91  0.72  O
 이OO        0.560  0.82  0.44  O
 박OO        0.311  0.61  0.15  X
```

**1등 점수가 아니라 1등과 2등의 간격을 봐야 한다.**
같은 라인 세대를 등록해 두고 이 화면을 켠 채 복도를 걸어보면
어디서 순위가 뒤집히고 어디서 붙는지가 그대로 보인다.
임계값은 이 화면에서 실측하고 정하는 게 순서다.

## 아파트 인접 세대 문제

이 설계의 최대 위험이다. 같은 라인 위아래층과 옆집은 보이는 AP 목록이
거의 같아서 커버리지만으로는 절대 안 갈린다.

**같은 자리에서 수집 라운드를 늘리는 건 답이 아니다.** 연속 스캔은 서로
강하게 상관돼 있어 12라운드나 40라운드나 정보량이 비슷하다. RSSI 측정 오차는
2~4dB이고 12라운드면 평균의 표준오차가 1dB까지 내려간다. 이미 충분하다.
문제는 노이즈가 아니라 신호 자체가 없는 것이다.

수집을 늘릴 거면 **다른 날, 다른 시간대로** 2~3회 나눠 찍는다.
하루 안의 변동보다 날짜 간 변동이 훨씬 크다. 병합은 지수이동평균으로 자동이다.

대신 여섯 겹으로 막는다.

### 1. 배송 순서로 후보 좁히기 (효과 최대)

FM 배송은 경로가 정해져 있다. 지금 위치가 200세대 아무 데나일 리 없고
"직전에 끝낸 집 다음 서너 곳" 중 하나다. 후보가 200개에서 4개로 줄면
2등 점수가 통째로 낮아져 마진이 저절로 벌어진다.

하드웨어도, 추가 수집도, 알고리즘 변경도 필요 없다.
회원 등록 시 순번을 넣고, 메인의 **배송 시작**으로 커서를 초기화한다.
발송이 확정될 때마다 커서가 전진한다. 순번 미지정 세대는 항상 후보에 남는다.

### 2. 기압계로 층 구분

인접 세대 오탐의 대부분은 옆집이 아니라 **위아래층**이다.
301호와 401호는 AP 구성이 거의 같지만 기압은 층당 약 0.33hPa 확실히 다르다.

**절대 기압은 못 쓴다.** 날씨로 하루에 10hPa씩 움직이는데 고도로는 80m,
아파트 25층 높이다. 그래서 동 입구에서 **1층 기준 설정**을 누르고
모든 값을 그 기준 대비 상대값으로만 비교한다. 기준은 6시간 후 만료된다.
기압계가 없는 기기에서는 이 단계가 자동으로 건너뛰어진다.

### 3. AP 희소성 가중 (IDF)

20세대 서명에 전부 등장하는 동 공용 AP는 변별력이 사실상 0이고,
한두 집에만 나오는 AP가 결정적이다. 문서 검색의 IDF와 같은 논리다.
**추가 수집 없이 이미 저장된 서명만으로 계산된다.**
서명이 서로 겹치는 아파트일수록 효과가 크다.

### 4. 표준편차 정규화

AP별 흔들림 정도를 함께 저장한다. "이 AP는 원래 ±2dB인데 5dB 어긋났다"와
"저 AP는 원래 ±10dB라 5dB는 의미 없다"를 구분한다.
수집을 조금 늘리는 게 실제로 도움이 되는 유일한 항목이다.

### 5. 신호 세기 가중 + 앵커 검사

가까운 AP일수록 크게 반영한다. 옆집으로 3m 옮기면 멀리 있는 AP는
거의 안 변하지만 문 안쪽 공유기는 확 떨어진다. 세대를 가르는 정보는
근거리 AP에만 있다. 서명 최강 AP 3개 중 2개가 안 보이면 감점한다.

### 6. 못 가르면 물어보기

여기까지 해도 진짜로 분리 안 되는 쌍은 남는다. 그때 조용히 보류하면
배송 완료 문자가 누락되고, 억지로 확정하면 오배송이 나간다. 둘 다 나쁘다.

점수는 충분한데 마진이 안 벌어지면 **"302호? 303호?"** 선택 알림이 뜬다.
한 번 탭이면 끝이고, 잘못 나간 문자보다 훨씬 싸다.

### 그래도 남는 원칙

**같은 라인 세대를 함께 등록해 둘수록 정확해진다.** 경쟁 후보가 있어야
애매한 상황을 애매하다고 판정할 수 있다. 보통 데이터가 늘면 혼동이
늘 것 같은데 여기서는 반대다.

`autoSend` 기본값이 꺼져 있는 이유도 같다. 나간 문자는 되돌릴 수 없다.

## 배송지 유형 — 사무실은 다르게 간다

회원마다 유형을 지정한다.

| 유형 | 동작 |
|---|---|
| 아파트·주택 | 문앞 서명으로 **자동 확정** → 문자 발송 |
| 사무실 | **구역까지만 자동**, 자리는 목록에서 탭 |
| 수동 | 자동 감지 제외 |

### 책상 단위 자동 감지는 넣지 않았다

인접 책상 간격이 1.5m인데 Wi-Fi 측위 오차는 3~5m다. **원리상 못 가른다.**
억지로 붙이면 옆자리에 완료 문자가 가거나, 마진 검사에 걸려 매번
"물어보기" 알림만 뜬다. 그럴 거면 목록에서 고르는 게 빠르다.

그래서 자동화는 구역 진입까지만 한다. 구역이 잡히면 알림이 뜨고,
탭하면 **그 구역 고객만** 큰 버튼으로 나온다. 오늘 이미 처리한 자리는
흐리게 표시되어 중복 탭을 줄인다.

이 방식의 값어치는 후보를 3~4명으로 줄여준 데 있다.
200명 목록에서 찾는 것과 4명 중에 고르는 것은 완전히 다른 일이다.
어차피 자리마다 서서 물건을 놓는 동작이 있으니, 그 김에 한 번 탭하는 게
오탐 걱정하며 임계값 튜닝하는 것보다 빠르고 정확하다.

### 구역 나누기가 정확도를 결정한다

**도면상 벽을 기준으로 나눈다.** 벽 하나가 5~15dB를 깎아 경계가 뚜렷해지므로
회의실·임원실처럼 막힌 공간은 오히려 아파트보다 잘 갈린다.
반대로 뻥 뚫린 오픈플로어를 눈대중으로 반 가르면 신호가 매끄럽게 변해
경계에서 계속 흔들린다.

구역 서명은 점이 아니라 면이다. **구역 안 서너 곳을 돌면서** 수집해야 한다
(30라운드, 자동으로 누적 병합). 한 자리에 서 있으면 그 지점 서명이 되어버린다.

5GHz AP는 감쇠가 빨라 2.4GHz보다 공간 해상도가 좋다. 수집 시 밴드를 함께 기록한다.

## NFC 태그 — Wi-Fi와 배타적이지 않다

바구니에 NFC 스티커를 붙이고 폰을 대면 그 고객에게 문자가 나간다.
태그마다 공장에서 구워진 고유 UID가 있어 변조가 안 되고,
태그 개수만큼 자동으로 구별된다. 별도 채번이 필요 없다.

### 둘 다 켜는 게 가장 정확하다

NFC는 "이 물건이 뭔가"를, Wi-Fi는 "지금 어디인가"를 답한다.
역할이 겹치지 않아서 서로를 검증한다. **고객별로 독립 스위치**를 둔 이유다.

| 조합 | 쓰는 경우 |
|---|---|
| 둘 다 켬 | 태그 부착에 동의한 아파트 고객 — 가장 정확 |
| NFC만 | 태그는 있는데 Wi-Fi 서명이 불안정한 곳 |
| Wi-Fi만 | 태그 부착 동의를 안 한 고객 |
| 둘 다 끔 | 수동 처리 |

### 교차 검증이 잡아내는 것

**태그는 물건에 붙어 있고, 물건은 옮겨진다.** 고객이 안으로 들였다가
옆집 앞에 잘못 내놓거나, 관리실에서 치우며 섞이면 엉뚱한 집에 문자가 간다.
NFC만 쓰면 이걸 알 방법이 없다.

태그를 찍으면 그 순간의 Wi-Fi 스캔을 그 고객의 서명과 대조한다.
점수가 너무 낮거나 다른 집이 확연히 높으면 **바로 보내지 않고 확인을 거친다.**

```
위치가 맞지 않습니다
태그는 김OO 님인데 현재 위치의 Wi-Fi 신호가 다릅니다.
이 위치는 박OO 님 쪽에 더 가깝습니다.
바구니가 옮겨졌을 수 있습니다. 그대로 보낼까요?
```

불일치는 `tag_location_conflict`로 적재된다. 특정 세대에서 자주 뜨면
바구니가 자주 옮겨지거나 서명이 노후한 것이라 사람이 봐야 한다.

### 반대 방향의 이득 — 공짜 정답 라벨

태그를 찍은 순간의 Wi-Fi 스캔은 **사람 손을 거치지 않은 확실한 정답**이다.
위치까지 일치한 건에 한해 자동으로 라벨이 쌓인다.
배송할 때마다 튜닝 데이터가 저절로 늘어난다는 뜻이다.
어긋난 건은 라벨로 넣지 않는다 — 오답을 정답으로 넣으면 학습이 망가진다.

### 태그 고를 때

- **NTAG213 / NTAG215** 권장
- 문앞이면 **방수·야외용** — 습기와 온도 변화로 몇 달 만에 죽는다
- 금속 바구니라면 반드시 **on-metal 태그**. 일반 태그는 금속에 붙이면 인식이 안 된다

앱이 꺼져 있어도 태그를 대면 배송 화면이 바로 뜬다
(`TECH_DISCOVERED` 인텐트 필터). 이를 위해 `NfcActivity`가 exported다.
인텐트 엑스트라를 신뢰하지 않고 태그 UID로 회원을 조회할 뿐이며,
위치가 어긋나면 확인 단계를 거친다.

### 먼저 정리할 것

남의 집 문앞 물건에 식별 태그를 붙이는 일이다.
**배송 완료 알림 서비스 가입 동의에 태그 부착 조항을 함께 넣는 게 깔끔하다.**

## 방문 예정 안내 + 광고

배송이 완료되면 **다음 순번 고객**에게 방문 예정 문자가 나간다.
순서가 반대면 안 된다 — 배송이 실패했는데 다음 고객이 기다리게 된다.
그래서 발송 성공 후에만 트리거된다.

```
[HY] 홍길동 고객님, 곧 프레시매니저가 방문할 예정입니다.
더 필요하신 것이 있으시면 미리 전화 주세요.
```

고객별 `방문예정 알림` 스위치로 켠다. 기본값은 꺼짐이다 —
받는 문자가 하루 두 통이 되므로 별도 동의 항목으로 봐야 한다.
같은 고객에게 12시간 내 중복 발송은 자동으로 막힌다.

### 광고를 붙이면 문자 전체가 광고성이 된다

가장 중요한 지점이다. **정보성 문자에 광고를 한 줄 섞으면
그 문자 전체가 영리목적 광고성 정보로 분류된다.**
배송 완료 문자라도 예외가 아니다.

그래서 광고 여부를 호출부 판단에 맡기지 않고 `MessageComposer`가 강제한다.
아래 조건을 하나라도 못 채우면 **광고 블록이 자동으로 빠지고
정보성 문자만 나간다.** 규제 위반 상태로 발송되는 경로 자체를 없앤 것이다.

| 조건 | 처리 |
|---|---|
| 고객별 광고 수신동의 | 미동의면 광고 제외 |
| 동의 후 2년 경과 | 재확인 필요 — 광고 제외 |
| 본문 앞 "(광고)" 표기 | 자동 삽입 |
| 무료 수신거부 안내 | 자동 삽입 (번호 미설정 시 광고 제외) |
| 야간 21시~익일 8시 | 광고만 제외, 정보성 문자는 정상 발송 |

**야간 조항이 이 서비스에서 특히 걸린다.** 새벽·이른 아침 배송이 돌면
8시 이전 발송이 일상적으로 발생하는데, 그 시간대에는 광고를 붙일 수 없다.
이 경우 광고만 떼고 배송 완료 문자는 그대로 나간다.

광고 수신동의는 배송 알림 동의와 **반드시 분리**해야 한다.
앱의 체크가 동의를 대신하지 않는다 — 가입서·녹취 등 실제 동의 근거는
회사가 따로 보관해야 하고, 앱의 기록은 그 사실을 참조하기 위한 것이다.
화면에도 그렇게 안내한다.

### 비용

광고와 수신거부 안내가 붙으면 90바이트를 넘어 **SMS가 아니라 LMS**로 나간다.
건당 단가가 오르고, 매일 배송이면 그대로 월 비용이 된다.
`문자 문구 설정` 화면에서 실제 나갈 본문과 바이트 수, SMS/LMS 여부를
저장 전에 미리 보여준다.

## 고객별 자동 문자 on/off

문자를 원치 않는 고객이 반드시 있다. 회원 탭 > **자동 문자 끄기**.

끄면 **감지와 배송 완료 처리, 경로 커서 전진은 그대로 되고 문자만 나가지 않는다.**
완료 경로가 넷이라(자동 확정 / 확인 모드 탭 / 구분 선택 / 구역 목록 탭)
각자 설정을 확인하게 두면 반드시 한 군데가 빠진다. 전부 `DeliveryCompleter`
한 곳을 통과하게 만들어서 누락이 구조적으로 불가능하게 했다.

목록과 알림에 "문자 끔"이 표시되고, 텔레메트리에는 `*_optout`으로 남는다.

## 테스트 모드 — 정답 만들고 알고리즘 고치기

메인 화면 **테스트 모드** 를 켜면 문자가 아예 나가지 않는다.
감지가 되면 발송 대신 정답 기록 알림이 뜬다.

### 1. 정답 찍기

두 경로가 있다.

- 라이브 매칭 화면 > **정답 기록** — 문앞에 선 채로 바로 찍는다 (빠름, 권장)
- 테스트 모드에서 감지 알림 탭 — 실제 탐지 흐름 그대로 검증할 때

화면에는 알고리즘의 1등 후보(이름 + 주소)와 판정, 점수, 마진이 뜬다.
버튼은 셋이다.

| 버튼 | 언제 |
|---|---|
| 맞음 | 1등 후보가 실제 배송지와 같음 |
| 다름 — 실제 배송지 선택 | 틀렸음. **실제 정답 세대를 골라준다** |
| 배송지 아님 | 복도·엘리베이터·이동 중 |

가운데 버튼이 중요하다. "아님"만 받으면 오답 하나가 늘 뿐이지만
"실제로는 302호였다"까지 받으면 302호에 대한 정답이 동시에 생긴다.
라벨 한 건의 값이 두 배가 된다.

**보류된 상황도 반드시 찍어야 한다.** 확정된 건만 모으면
임계값을 낮췄을 때 어떻게 되는지를 계산할 도리가 없어서
결과가 한쪽으로만 나온다. 옆집 앞, 복도, 아래층에서도 찍어야
"여기서는 보내면 안 된다"는 정보가 들어온다.

### 2. 알고리즘 업데이트

메인 > **알고리즘 업데이트**. 라벨 30건 미만이면 버튼이 잠긴다.
100건 넘어야 결과가 안정된다.

무슨 일이 일어나는지 정확히 말하면 — **신경망을 얹는 게 아니다.**
점수 함수의 계수 아홉 개(점수·마진 임계, 최소 커버리지, RSSI 허용폭,
커버리지 비중, AP 희소성, 편차 정규화, 층 허용치·감점)를 다시 잡는다.
축이 늘어 전수 격자는 단말에서 몇 분씩 걸리므로 **좌표 하강**을 쓴다 —
한 축씩 순서대로 최적화하고 두 바퀴 돈다.
라벨 수십~수백 건 규모에서 자유도 높은 모델을 태우면 그 동, 그 시간대,
그 단말에만 맞는 값이 나오고 다른 데 가면 무너진다.

두 가지를 지킨다.

**비대칭 비용** — 오배송 1건을 문자 누락 5건과 같은 무게로 친다.
정확도나 F1로 최적화하면 둘을 같게 취급해서 엉뚱한 값이 나온다.
`ParamTuner.DEFAULT_FP_COST`에서 조정한다.

**5겹 교차검증** — 같은 데이터로 파라미터를 고르고 그 데이터로 성능을 재면
반드시 좋아 보인다. 화면 위쪽에 나오는 **교차검증 성능**이 처음 보는
데이터에서 기대되는 값이고, 판단은 이 숫자로 해야 한다.
아래쪽 "전체 라벨에 맞춘 성능"은 참고용이다.

결과는 자동 적용되지 않는다. 현재값과 나란히 보고 직접 적용을 누르며,
되돌리기는 언제든 가능하다. 튜닝이 늘 개선인 건 아니라서
"개선 없음"이 뜨면 적용하지 않는 쪽이 맞다.

### 3. 한계

- 라벨을 한 동에서만 모으면 그 동에만 맞는 값이 나온다. 여러 단지를 섞어야 한다.
- 배송 순서 좁히기는 튜너가 시뮬레이션하지 않는다. 즉 **실제 운영 성능은 화면에 표시되는 값보다 좋다.** 보수적인 방향이라 그대로 뒀다.
- 서명을 재수집하면 과거 라벨의 전제가 바뀐다. 대량 재수집 후에는 라벨도 다시 모으는 게 안전하다.
- 라벨은 `라벨 내보내기`로 JSON 백업이 되고, 텔레메트리로 BigQuery에도 쌓인다.

## 튜닝 포인트

매칭 계수는 이제 상수가 아니라 `MatchParams`에 들어 있고,
알고리즘 업데이트가 이 값들을 바꾼다. 손으로 고칠 일은 거의 없다.

| 파라미터 | 기본값 | 의미 |
|---|---|---|
| `scoreThreshold` | 0.62 | 확정 최소 점수 |
| `marginThreshold` | 0.10 | 1·2등 최소 점수 차 |
| `minCoverage` | 0.55 | 서명 AP 중 보여야 할 비율 |
| `rssiTolerance` | 18.0 | 이만큼 어긋나면 0점 (dB) |
| `coverageWeight` | 0.35 | 최종 점수에서 커버리지 비중 |
| `anchorPenalty` | 0.5 | 앵커 미충족 시 감점 계수 |
| `idfWeight` | 0.6 | AP 희소성 반영 정도 (0이면 끔) |
| `stdWeight` | 0.5 | 표준편차 정규화 정도 (0이면 끔) |
| `floorToleranceHpa` | 0.25 | 층 판정 허용 오차 (0.33이 한 개 층) |
| `floorPenalty` | 0.35 | 층 불일치 시 감점 (1.0이면 층 판정 끔) |

튜너가 이 값들을 전부 학습한다. **어떤 장치가 이 현장에서 해롭다면
해당 가중치가 스스로 0으로 수렴한다.** 예를 들어 단독주택 위주 경로에서는
`floorPenalty`가 1.0(끔)으로 수렴할 가능성이 높다.

아래 둘은 여전히 코드/설정 화면에 있다.

| 값 | 위치 | 기본값 | 의미 |
|---|---|---|---|
| `minConsecutiveHits` | DwellTracker | 3 | 연속 일치 횟수 |
| `dwellSeconds` | 설정 화면 | 90 | 체류 인정 시간 |

파일럿에서는 확인 모드로 돌리면서 알림이 뜬 건과 실제 배송 건을 대조해
`SCORE_THRESHOLD`와 `MARGIN_THRESHOLD`를 올리는 방향으로 잡는 게 안전하다.
문자를 못 보내는 것보다 잘못 보내는 쪽이 훨씬 비싸다.

## 데이터 적재 (BigQuery)

```
앱 → 로컬 NDJSON 큐 → (15분 주기 WorkManager) → Cloud Run 함수 → BigQuery
```

**앱이 BigQuery에 직접 쓰지 않는다.** 그러려면 서비스 계정 키를 APK에 넣어야 하는데
APK는 언제든 디컴파일된다. 키 하나 유출되면 웨어하우스 쓰기 권한이 통째로 나간다.
BigQuery 권한은 함수의 서비스 계정에만 준다.

배송 현장은 지하주차장·엘리베이터에서 네트워크가 수시로 끊기므로
전송 실패 시 버리지 않고 로컬 NDJSON에 쌓아두었다가 배치로 밀어 올린다.
큐 적체 건수는 라이브 매칭 화면 하단에 표시된다.

### 적재되는 이벤트 세 가지

| 이벤트 | 내용 |
|---|---|
| `signature_collected` | 수집 라운드 수, AP별 평균 RSSI·관측 빈도 |
| `match_evaluated` | **평가 1회마다** 1·2등 점수, 마진, 확정 여부, 보류 사유 |
| `notification_sent` | 발송 모드(auto/confirm), 성공 여부, 체류 시간 |
| `label_recorded` | 사람이 찍은 정답 — 예측/실제/판정 |

`match_evaluated`가 이 프로젝트에서 제일 값어치 있는 데이터다.
확정된 건만 남기면 안 되고 **보류된 건까지 전부** 남아야 한다.
그래야 "임계값을 0.70으로 올렸다면 오탐이 몇 건 줄었을까"를
현장 재수집 없이 오프라인에서 계산할 수 있다.
`server/schema.sql` 하단에 임계값 스윕·혼동 세대쌍·서명 노후화 질의를 넣어뒀다.

### BSSID는 해시해서 올라간다

고객 집 공유기 MAC 주소가 웨어하우스에 평문으로 쌓이면 특정 가구와
연결 가능한 식별자가 된다. 분석 목적으로는 원본이 전혀 필요 없으므로
단말에서 솔트 SHA-256으로 바꿔 올린다. 원본 BSSID는 단말 로컬에만 남는다.
전화번호와 주소는 아예 올리지 않는다 — `member_id`만 나간다.

### 배포

```bash
# 1. BigQuery
sed 's/PROJECT_ID/실제프로젝트/' server/schema.sql | bq query --use_legacy_sql=false

# 2. 수집 함수
cd server && gcloud functions deploy wifi-delivery-ingest \
  --gen2 --runtime=python312 --region=asia-northeast3 \
  --source=. --entry-point=ingest --trigger-http \
  --set-env-vars=BQ_PROJECT=실제프로젝트,BQ_DATASET=wifi_delivery
```

## 남은 작업

- **발송 경로 교체** — `SmsSender.send()`를 사내 문자발송 플랫폼 API 호출로 바꾸면
  대표번호 발신, 발송 이력 중앙 집계가 된다. 호출부는 그대로 두면 된다.
- **하이브리드 판정** — GPS(단지·동) + 기압계(층) + Wi-Fi(세대)를 AND로 걸면
  Wi-Fi 단독보다 임계값을 느슨하게 가져가면서도 오탐이 준다.
- **서명 서버 동기화** — 지금은 단말 로컬 JSON이다. 담당자 교체·기기 변경 시 유실된다.
- **배터리** — 30초 주기 종일 스캔의 실제 소모량을 파일럿에서 측정해야 한다.

## 권장 진행 순서

0. 회원별 배송지 유형 지정 — 사무실 건은 구역 등록 후 배정
1. 테스트 모드 ON, 회원 10~20세대 등록 (**같은 라인 세대를 반드시 섞을 것**, 배송 순번 입력)
2. 동 입구에서 **1층 기준 설정** → 각 세대 문앞에서 서명 수집
3. 라벨링 — 대상 세대, 옆집, 위아래층, 복도에서 골고루 100건 이상
4. 알고리즘 업데이트 → 교차검증 수치 확인 → 적용
5. 테스트 모드 유지한 채 라벨 더 모아 재검증
6. 오배송이 충분히 낮으면 테스트 모드 OFF, 확인 모드로 실배송 투입
7. 확인 모드에서 몇 주 운영 후 자동 발송 검토

## 반드시 먼저 확인할 것
